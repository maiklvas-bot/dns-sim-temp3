# Мастер кейсов «Космонавт» — дизайн

**Дата:** 2026-08-02
**Статус:** согласован со стейкхолдером, готов к декомпозиции на планы

## Задача

Дать методологу единый инструмент создания и правки кейсов, который **сам не даёт нарушить правила**
и **объясняет методологию по ходу дела**, а не требует прочитать её заранее.

Сегодня автор работает через визард из 4 шагов (только контекст и первый цикл) и полный редактор из
3 вкладок. Ни один не объясняет, зачем нужна скрытая причина, почему нельзя выставить произвольный
балл и что делает кейс проходимым без диагностики. Результат измерим: в 14 существующих кейсах
**407 замечаний автопроверки**, все три содержательные проверки срабатывают на 14 из 14.

**Пользователь:** методолог или HR, который создаёт кейсы, но не погружён в устройство симуляции.
Он не знает слов «BARS», «антигейминг», «стоп-фактор» — и не обязан знать.

## Ключевые решения

| Решение | Выбор | Следствие |
|---|---|---|
| Что такое «матрёшка» | Ветвление: ответ определяет следующий шаг | Модель уже умеет (`nextCycleId`), нужен UI. Новых сущностей не требуется |
| Роль эталонных кейсов | И учебник, и точка старта | Одна сущность вместо двух: посмотрел → «взять за основу» → правишь |
| Содержание анкеты | Всё, сгруппированное по этапам | Анкета — зеркало мастера, а не отдельная форма |
| Судьба старого UI | Мастер заменяет и визард, и редактор | Мастер обязан вобрать **все** возможности старого редактора |
| Навигация | Гибрид | Новый кейс — по шагам; существующий — сразу анкета-хаб |

## Архитектура

### Пять этапов

Каждый этап отвечает на один вопрос автора и соответствует одному блоку анкеты.

**1. Замысел** — зачем этот кейс существует.
Название, описание, проверяемые компетенции (основные и дополнительные), бизнес-проблема.
Здесь же — выбор эталона как заготовки.

**2. Ситуация** — что видит участник и что от него скрыто.
Контекст, сигнал (тип, источник, текст), зоны магазина, **скрытая причина, данные для запроса
с ценой, ложные следы**. Это содержимое паспорта кейса — то, без чего кейс проходится без
диагностики.

**3. Структура** — как кейс разворачивается.
Выбор: линейная последовательность или ветвление. Количество шагов. Схема переходов между
циклами. Здесь автор видит, куда ведёт каждый ответ, и где ветка обрывается.

**4. Решения** — что может сделать участник.
Варианты ответов по циклам, уровень проявления каждой компетенции (слабо/средне/сильно),
эффекты на метрики магазина, целевой цикл для каждого ответа.

**5. Оформление и запуск** — готов ли кейс.
Медиа (изображения, озвучка), тайминги, канал, порядок показа, результат автопроверки,
статус готовности.

Этап 5 существует именно потому, что мастер заменяет старый редактор: всё, что тот умел
(`CaseMediaPanel`, тайминги, `sortOrder`, `isActive`), должно найти место здесь, иначе
функциональность потеряется.

### Анкета-хаб

Одна страница, пять блоков в порядке этапов. Каждый блок:

- показывает **суть заполненного**, а не отметку «готово»: не «компетенции ✓», а «Организация
  и контроль (вес 13.2)»;
- **кликается** и открывает свой этап;
- **подсвечивает проблемы** своего этапа с их количеством.

```
┌─ 1. ЗАМЫСЕЛ ────────┐  ┌─ 2. СИТУАЦИЯ ───────┐
│ Очередь на кассе    │  │ Сигнал: сообщение   │
│ Организация (13.2)  │  │ Скрытая причина ✓   │
│              ▸ ⚠ 1  │  │ Данных: 2, следов:1 │
└─────────────────────┘  └─────────────────────┘
┌─ 3. СТРУКТУРА ──────┐  ┌─ 4. РЕШЕНИЯ ────────┐
│  [1]─┬─▸[2A]        │  │ 3 варианта          │
│      └─▸[2B]─▸[3]   │  │ слабо/средне/сильно │
│  ветвление, 4 шага  │  │              ▸ ⚠ 2  │
└─────────────────────┘  └─────────────────────┘
┌─ 5. ЗАПУСК ─────────────────────────────────┐
│ Черновик · 3 замечания мешают публикации    │
└─────────────────────────────────────────────┘
```

**Навигация:** новый кейс ведётся по шагам 1→5 (новичок не должен гадать, с чего начать).
Существующий кейс открывается сразу анкетой. После завершения шагов автор тоже попадает на анкету.

**Где живёт мастер.** Полноэкранный диалог из вкладки «Кейсы» админки — там же, где сейчас
открывается редактор (`Dialog` в `AdminWorkspaceRuntime`). Отдельный маршрут не заводим: кейс
редактируется в контексте списка, а модальное окно уже используется для этого сегодня.

**Судьба файлов старого UI.** `CaseCreationWizard.tsx` удаляется — его роль полностью переходит
к этапам мастера. `EntityEditor.tsx` **остаётся**, но теряет ветку `mode === "case"`: он продолжает
обслуживать email, messenger и video-кейсы, у которых своя структура и свой редактор. Попытка
затащить и их в мастер вышла бы за рамки задачи — мастер проектируется под главные кейсы.

## Обучающий слой

Три уровня, не мешающие опытному автору.

**Уровень 1 — подсказка у поля.** Одна строка простым языком, без терминов системы.
Не «заполните скрытую причину», а «Что на самом деле стоит за симптомом? Участник этого не видит —
он должен догадаться сам».

**Уровень 2 — эталон рядом.** На каждом этапе кнопка «как в образце» показывает этот же этап
эталонного кейса, не уводя со страницы. Автор видит, как выглядит хорошо заполненный шаг.

**Уровень 3 — разбор ошибки в контексте.** Ключевое требование: ошибка показывается **там, где она
живёт, средствами оформления и логики**, а не абзацем текста.

Пример для антигейминга на этапе «Решения»:

```
           Слабо  Средне  Сильно
Планирование  1  →   3  →   5     ↗ растёт
Коммуникация  1  →   3  →   5     ↗ растёт
                                   ⚠ все линии параллельны

«Правильный ответ виден по форме: чем "лучше" вариант, тем выше все компетенции.
 Участник выберет последний, не думая.
 Как починить: пусть сильный по планированию будет средним по коммуникации —
 тогда это профиль, а не лестница.»                        [Показать в образце]
```

Аналогично: тупиковая ветка подсвечивается **на схеме структуры**; отсутствие данных видно
**в блоке ситуации** как пустое место, где участнику нечего расследовать.

## Проверки и работа с замечаниями

Используются четыре существующие проверки (`validateCase` в `shared/case-validation.ts`):
соответствие уровням BARS, антигейминг, диагностика, реальность эффектов. Механика не меняется.

Меняется **подача**. Каждое замечание получает четыре части:

1. **Что не так** — на языке автора, без терминов системы
2. **Почему это ломает оценку** — какой дефект появится у участника
3. **Как исправить** — конкретное действие
4. **Где это** — привязка к этапу и полю, клик ведёт прямо туда

**Осознанный отказ.** Автор может пометить замечание как принятое — с обязательным комментарием,
почему в этом кейсе так и задумано. Тогда замечание перестаёт блокировать, но остаётся видимым:
в анкете отображается «1 замечание принято автором». Это закрывает требование «или отказаться»
и не превращает проверки в непреодолимую стену.

Хранение: новое поле `acceptedIssues` в модели кейса — список `{ check, cycleId?, optionId?, reason }`.
`shouldBlockCaseSave` учитывает принятые замечания при решении о блокировке.

## Эталонные кейсы

4–5 кейсов в идеальной логике, покрывающих разные ситуации розницы: конфликт с клиентом, сбой
процесса, делегирование, приоритеты под давлением, работа с новичком.

**Хранение:** отдельный JSON в репозитории (`script/case-templates.json`), не в БД. Причины:
эталон — неизменяемый учебный материал; он версионируется в гите вместе с методологией; он не
засоряет список рабочих кейсов админки.

**Две роли:**
- **учебник** — открывается на просмотр с любого этапа мастера («как в образце»);
- **точка старта** — кнопка «взять за основу» создаёт черновик с той же структурой и связями,
  тексты автор переписывает под свою ситуацию.

Каждый эталон обязан проходить автопроверку без замечаний — это гарантируется тестом, иначе
учебный материал будет учить плохому.

## Миграция

14 существующих кейсов открываются в мастере через анкету и сразу показывают свои замечания.
Ничего не ломается: контент продолжает работать, просто становится видно его качество.

Публикация **не ужесточается** этим дизайном: кнопка «Опубликовать» по-прежнему не требует
прохождения гейта, иначе 14 кейсов с 407 замечаниями станут непубликуемыми. Переход к строгой
публикации — отдельное продуктовое решение после миграции контента.

## Что переиспользуется

Существенная часть уже построена и не требует переписывания:

| Есть | Роль в мастере |
|---|---|
| `validateCase`, `hasMeaningfulText`, `BARS_OPTIONS` (`shared/`) | Механика проверок и уровней — без изменений |
| `CaseFlowDiagram.tsx` (116 строк) | Схема структуры: уже умеет ветвление, `__complete`, переходы по порядку |
| `StructuredOptionsEditor.tsx` | Редактор вариантов с BARS-пикером → этап «Решения» |
| `CaseDossierEditor.tsx` | Поля диагностики → этап «Ситуация» |
| `CaseValidationPanel.tsx` | Основа для разбора замечаний (нужно дополнить объяснениями) |
| `CaseMediaPanel.tsx` | Медиа → этап «Оформление» |
| `buildCaseDossierSummary` | Сводка заполненности → блок анкеты |

## Декомпозиция на планы

Три плана, каждый даёт работающий результат:

**План 1 — каркас.** Пять этапов, анкета-хаб, навигация (шаги для нового, хаб для существующего),
перенос всех возможностей старого редактора, замена визарда и редактора точкой входа. Обучающий
слой — только подсказки у полей (уровень 1).

**План 2 — обучающий слой.** Разбор замечаний с объяснениями и привязкой к полям, визуализация
ошибок в контексте (лестница компетенций, тупики на схеме), механика осознанного отказа
(`acceptedIssues`).

**План 3 — эталоны.** 4–5 кейсов в JSON, режим просмотра «как в образце», кнопка «взять за основу»,
тест на то, что каждый эталон проходит автопроверку чисто.

Порядок обязателен: план 2 опирается на этапы из плана 1, план 3 — на оба.

## Что не входит

- **Дебриф** — отдельная подсистема, ждёт согласования концепции.
- **Ужесточение публикации** — продуктовое решение после миграции контента.
- **Изменение самих проверок** — механика уже вычищена ревью, дизайн меняет только подачу.
- **Автогенерация кейсов по параметрам** — эталоны пишутся вручную как выверенный учебный материал.
