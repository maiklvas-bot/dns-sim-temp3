## 1. Проблема

В кодовой базе SimCenter/ЗРД одновременно существуют:
1. Токены shadcn в `tailwind.config.ts` (HSL-переменные `--background`, `--primary` и т.д.) — архитектура правильная, но **значения** не сверялись с настоящим брендом DNS.
2. Отдельная, несвязанная система `--dns-visual-*` в `visual-system.css` (хардкод-хекс).
3. Точечные хардкод-хексы (`bg-[#0d1117]`, `border-[#2a3a4e]` и т.п.) в `admin.css`/`assessor.css`/`simulation.css`/`zrd.css`.
4. Светлая тема реализована не как второй набор токенов, а как список `!important`-переопределений в `.dns-product-shell.dns-theme-light` (`base.css:874-934`), который вручную ищет конкретные хардкод-хексы. Любой новый хардкод в компоненте молча ломает светлую тему.
5. Значения дрейфовали от настоящего бренда: тёмный фон сейчас `#0d1117` (generic dev-tool чёрный), настоящий брендовый navy — `#001145`. Primary-оранжевый `#FF6B00` близок, но не совпадает с брендовым `#f68b1f`.

## 2. Цель v1

Один источник правды для цвета/типографики/радиусов на весь SimCenter (ЗРД и РРС Тюмень — вне охвата этого захода), **два деликатно спроектированных семантических набора** (тёмный и светлый — не инверсия друг друга), витрина в приложении для сверки, и Figma-файл для компоновки экранов — отдельно от `DNS-BrandStyleSystem`, который остаётся презентационной/слайдовой системой.

## 3. Не входит в v1 (backlog)

- ЗРД (`zrd.css`) и РРС Тюмень дашборд — отдельные заходы после фундамента.
- Автоматизация токенов (Tokens Studio / Style Dictionary / CI) — нет масштаба, оправдывающего эту инфраструктуру.
- Figma Code Connect — требует Dev Mode seat, избыточно при текущей задаче.
- Полная разовая замена всех хардкод-хексов — миграция идёт по факту правок конкретных файлов, не одним махом.

| Роль | Класс | Кегль | Где использовать |

| Заголовок секции | `text-xl` / `text-lg` | 20px / 18px | H2/H3 внутри карточек |

## 12. Моушен — длительности и easing

Сейчас длительности анимаций разбросаны как попало: 15 разных значений в `base.css` (160/180/150/140/200/300/900/400/320/120/850/560/500/420/340ms), без единой системы — визуально незаметно, но затрудняет предсказуемость и поддержку. Фиксируем 3 именованных токена, новые анимации используют их, старые литералы мигрируют по мере правок (тот же принцип, что и с хардкод-хексом — не одним махом):

```css
--duration-fast: 150ms;   /* hover, мелкие переходы состояний */
--duration-base: 200ms;   /* стандартный переход (появление панели, fade) */
--duration-slow: 320ms;   /* крупные переходы (модалки, слайд-ин тостов) */
--ease-standard: cubic-bezier(0.4, 0, 0.2, 1);
```

Существующий глобальный transition (`base.css:1994-1996`, 180ms ease) округляется до `--duration-fast`+`--ease-standard` при миграции.

## 13. Z-index — шкала слоёв

Реальные кластеры использования: `z-10` (13), `z-20` (8), `z-50` (29, доминирует), плюс случайные `z-30`, `z-40`, `z-[60]`, `z-[100]`, `z-[1]` — то есть система негласно уже почти сложилась, но выбросы (`z-[60]`, `z-[100]`) — признак, что кому-то не хватило `z-50` и он просто прибавил произвольное число. Формализуем:

| Токен | Значение | Назначение |
|---|---|---|
| `--z-raised` | 10 | Приподнятые карточки, hover-эффекты |
| `--z-sticky` | 20 | Sticky-шапки, липкие панели |
| `--z-dropdown` | 30 | Дропдауны, поповеры |
| `--z-overlay` | 50 | Модалки, диалоги (текущий фактический максимум) |
| `--z-toast` | 60 | Тосты/уведомления — **выше** модалок всегда |
| `--z-tooltip` | 70 | Тултипы — всегда самый верхний слой |

Точечные `z-[100]`/`z-[1]` мигрируют на ближайший подходящий токен по мере правок соответствующих компонентов.

## 17. Отзывчивость (responsive)

Не вводим новую шкалу breakpoint'ов — используются дефолтные Tailwind (`sm/md/lg/xl/2xl`), что и сейчас имплицитно так. На уровне компонентов уже применяется **container queries** (`container-type: inline-size` в `.dns-store-map`, `base.css:16`) — это осознанный паттерн для компонентов, которые должны реагировать на размер родителя, а не вьюпорта. Канон: **breakpoints — для уровня страницы, container queries — для самодостаточных виджетов** (карты, карточки, панели, которые переиспользуются в разных по ширине местах).

## 18. Доступность — базовая планка

Оба набора токенов (тёмный и светлый) должны держать контраст текст/фон не ниже **WCAG AA (4.5:1 для обычного текста, 3:1 для крупного/UI-элементов)**. Это ограничение, а не новый токен — проверяется при визуальной сверке на этапе 2 порядка внедрения (п.19), а не постфактум.
