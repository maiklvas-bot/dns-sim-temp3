# SimCenter: сверка ТЗ «проверка идеи симуляции» со всей платформой — закрытость смыслов

> Рабочий документ для обсуждения со стейкхолдерами. Задача — не переписать исходное ТЗ
> (`tz_plan_proverki_simulyacii.pdf`, далее «ТЗ-0»), а проверить каждый его тезис на то, что уже
> закрыто **во всей платформе SimCenter**, а не в одном её модуле, и дать честную базу для решения
> по разделу 19 ТЗ-0 («продолжаем / упрощаем / уточняем запрос / останавливаем»).
>
> **Важная поправка после первой версии этого документа:** первая версия ошибочно разбирала только
> модуль ЗРД. Платформа шире — это карьерная лестница симуляций:
> ```
> Космонавт (линейный сотрудник, оценка готовности) — доступен, самый развитый модуль
>   → Заместитель управляющего — в разработке, контента нет
>     → Управляющий — в разработке, контента нет
>       → ЗРД (замрегдиректора) — доступен, самый новый модуль
> ```
> (`client/src/features/assessor/assessor-constants.ts` → `SIMULATION_ROLE_CARDS`). Дальше разбор
> идёт по всей лестнице, а не по одному модулю.

Статусы: 🟢 закрыто (есть решение и источник) · 🟡 частично (есть кусок, не вся глубина) ·
🔴 открыто (нет ответа в проекте, нужно решение/данные).

## 0. Главный вывод

На платформе **два разных движка кейсов**, выросшие независимо:

| | Космонавт | ЗРД |
|---|---|---|
| Модель кейса | `SimCase` → `CaseCycle` (ветвление через `nextCycleId`) → `CaseOption` (скоринг по компетенции + эффекты на метрики), мультиканально: очное/email/мессенджер/видео | `EventCard` — один узел, 2–4 варианта, без ветвления |
| Конструктор без кода | ✅ есть: `CaseCreationWizard` + `StructuredCyclesEditor` + `StructuredOptionsEditor` + `SignalCreationWizard` (админка) | ❌ нет: контент только в коде (`shared/zrd/content*.ts`) |
| Формат | Диагностический кейс (кризис → сигнал → выбор → следующий цикл) | Экономическая стратегия (ресурсы → показатели, контекстная уместность решения) |
| Дебриф / перенос в работу | 🔴 нет | 🔴 нет |
| Явная бизнес-проблема (не «оценка готовности» вообще, а конкретный измеримый разрыв) | 🔴 нет | 🔴 нет |

**Вывод:** платформа не страдает от отсутствия инструментов (конструктор кейсов уже собран и
работает на Космонавте) — она страдает от того, что **методические гейты ТЗ-0 (G1 запрос,
G2 формат, G6 дебриф) не пройдены ни для одного модуля**, и от того, что **два модуля используют
несовместимые движки кейсов**, так что усиление одного (например, конструктора) не подтягивает
автоматически другой.

## 3. Что реально открыто (нужны твои решения, не мои гипотезы)

### 3.1. Бизнес-проблема (G1) — платформенный уровень
«Оценка управленческой готовности» — это цель инструмента, не диагностированный разрыв. ТЗ-0
спрашивает конкретнее: **что сотрудник должен делать иначе после прохождения, и как поймём, что
изменилось в реальной работе**. Этого нет ни для Космонавта, ни для ЗРД.

**Вопрос:** есть ли у компании (регдиректора/HR/твои наблюдения) зафиксированный разрыв в
поведении — по любой ступени лестницы (линейный → зам.управляющего → управляющий → ЗРД), — который
и запустил идею всей платформы? Или задача платформы как раз в том, чтобы такой разрыв выявлять
(тогда бизнес-проблема формулируется иначе: «нет системного инструмента диагностики управленческой
готовности на каждой ступени карьеры»)?

### 3.2. Единая модель кейса или два разных жанра — архитектурное решение
Два движка кейсов независимо развились под два разных жанра: диагностический кризис-кейс
(Космонавт) и экономическая стратегия (ЗРД). Возможные пути:
- **(a)** Осознанно оставить два жанра — они оценивают разные грейды по-разному (линейный
  сотрудник тушит кризисы здесь и сейчас; ЗРД управляет регионом стратегически) — это может быть
  правильно педагогически, не поверхностной случайностью.
- **(b)** Перенести конструктор Космонавта и на «Заместителя управляющего»/«Управляющего» (пока
  без контента) как единую линию кейс-based модулей, оставив ЗРД отдельным экономическим жанром на
  вершине лестницы.
- **(c)** Унифицировать всё под один движок.

**Вопрос:** какая из веток лестницы (Космонавт → зам.управляющего → управляющий) должна
использовать существующий конструктор кейсов Космонавта, когда до неё дойдут руки? Это определяет,
стоит ли сейчас усиливать методологию именно конструктора Космонавта (раздел 4) или чего-то ещё.

### 3.3. Усиление конструктора кейсов методическими гейтами ТЗ-0
Конструктор уже есть технически. Не хватает того, что ТЗ-0 называет «диагностическим мастером»:
обязательных вопросов/полей на скрытую причину, данные для запроса, ложные следы, антигейминг-чек
перед публикацией кейса, дебриф-вопросы.

**Вопрос:** это делаем как усиление существующего `CaseCreationWizard` (добавить шаги/поля —
относительно небольшая доработка существующего кода), или как отдельный «методический слой»
(чек-лист вне кода, которым методолог/HR пользуется вручную перед вводом в мастер)? Ты подтвердил,
что кейсы должен уметь добавлять методолог/HR без доступа к коду — значит, доработка должна жить в
самой админке, не в документации для разработчика.

### 3.4. Дебриф и перенос в работу (G6, раздел 14 ТЗ-0)
Отсутствует полностью на обеих ветках. Это не только фича экрана — это ещё организационный вопрос:
кто в компании берёт «рабочее действие на 7 дней» и проверяет его выполнение вне симуляции.

**Вопрос:** дебриф — это то, что должно жить **внутри продукта** (экран после кейса/партии с
вопросами и полем вывода), или это процесс **вне продукта** (руководитель/HR обсуждает результат
с участником очно, продукту нужно только выгрузить материал для такого разговора — то есть по сути
уже есть, это PDF-отчёт)? От ответа зависит, нужна ли новая функциональность вообще, или нужно
только обогатить существующий PDF-отчёт вопросами для дебрифа.

### 3.5. Методическая база (раздел 18 ТЗ-0)
Kirkpatrick, Kolb, Spencer & Spencer и остальные источники существуют только в твоём рассуждении —
не зафиксированы как заметка в Obsidian, не связаны wikilink’ами с `proekt-zrd`/`proekt-simcenter`.
При следующей итерации это придётся воссоздавать заново по памяти.

**Вопрос:** сохранить это рассуждение отдельной заметкой в `claude-kb/raw/` (с пометкой «не канон,
черновик обоснования») со ссылкой из обоих проектных канонов? Могу сделать сам по подтверждению.

## 4. Предложение (не решение — база для раздела 19 ТЗ-0)

Не «упрощаем» и не «останавливаем» — оба движка (диагностический и экономический) инженерно
сильны и не дублируют друг друга бессмысленно. Предлагаю **«уточняем запрос»** по четырём пунктам
выше (3.1–3.4), в этом порядке приоритета:

1. **3.1 (бизнес-проблема)** — без ответа здесь всё остальное строится на предположении.
2. **3.2 (архитектурное решение по лестнице)** — определяет, инвестируем ли в расширение
   конструктора Космонавта или держим ЗРД отдельно.
3. **3.4 (дебриф)** — минимально дешёвый шаг: обогатить существующий PDF-отчёт, не строить новый
   экран.
4. **3.3 (методические гейты в конструкторе)** — самая трудоёмкая доработка, имеет смысл делать
   после 3.1–3.2, чтобы не переделывать.

Раздел 3.5 — отдельная, не блокирующая задача (фиксация знаний), можно сделать в любой момент.
