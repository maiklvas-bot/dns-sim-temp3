## 2. Назначение

DNS SimCenter — платформа бизнес-симуляций для оценки и развития управленческой готовности в рознице DNS. Основной модуль «Космонавт» моделирует рабочий день магазина и формирует профиль компетенций участника. Отдельный модуль ЗРД — стратегическая экономическая симуляция управления регионом с многоместным матчем, серверно-авторитетным движком и профилем из 12 компетенций. Оценщик запускает и наблюдает live-сессии, администратор управляет контентом, результатами и медиа, участник проходит симуляцию; итог доступен в интерфейсе и PDF.

### 2.1. Бизнес-контекст жизненного цикла сотрудника

SimCenter не является самостоятельным однократным assessment flow. Он должен встраиваться в полный карьерно-учебный путь:

1. трудоустройство, адаптация, тест по должности и выход с испытательного срока;
2. развитие в должности, УСМ+/УСМ−, ДПР, рабочие показатели и переходы УОТ;
3. «Космонавтика»: входной ассессмент, отбор, обучение, выходной ассессмент и кадровый резерв;
4. возможное назначение ЗУМ;
5. подготовка через Школу УМ до назначения либо обязательное прохождение ближайшего курса после назначения без неё;
6. должность УМ и «Адаптация УМ» для доращивания или обновления навыков;
7. «Институт ЗРД»: входной ассессмент, обучение, выходной ассессмент и возможность претендовать на должность ЗРД.

Оценка, прохождение обучения, изменение УОТ, включение в резерв и назначение на должность являются разными событиями и не должны сливаться в один автоматический статус. Каноническое бизнес-описание ведётся в Obsidian: `01-projects/simcenter/EMPLOYEE-DEVELOPMENT-JOURNEY.md`.

## 3. Главные цели

1. Довести оценку «Космонавта» до методически защищённого и технически воспроизводимого состояния.
2. Сохранить и развивать live-сессии, админ-контент, отчётность и безопасное хранение производственных данных.
3. Довести модуль ЗРД от рабочего интерфейса/мультистола до кабинета оценщика, экспертной сверки и пилота.
4. Вести проверяемую историю решений и шагов в репозитории и Obsidian.

## 4. Что нельзя сломать

- существующий контент и SQLite — источник истины; не заменять содержимое внешними архивами без отдельной задачи;
- `storage/` и `uploads/` переживают обновления; seed с `--force`, restore и удаление данных требуют явного решения и резервной копии;
- live-сессии, токены участника/ЗРД и восстановление незавершённой сессии;
- аутентификацию персонала, CSRF, rate limiting, hardened cookies и исключение секретов из Git;
- сопоставимость результатов: изменения шкал, профилей и набора кейсов требуют версии/маркировки;
- живая ZRD Wiki: изменение механики одновременно обновляет `docs/zrd-wiki/` и `14-changelog.md`;
- незакоммиченные изменения текущего worktree нельзя перезаписывать, смешивать или терять.

## 5. Технический стек

- **Frontend:** React 18, TypeScript, Vite, Tailwind CSS, TanStack Query, Recharts, Three.js.
- **Backend:** Express 5, TypeScript, WebSocket/live-session services.
- **Database:** SQLite, better-sqlite3, Drizzle ORM, SQL migrations.
- **Reports:** backend PDF generator (`server/generate_pdf.py`).
- **CI:** GitHub Actions, Ubuntu, Node.js 20; lint/typecheck, smoke, build, Playwright, safety contracts, Docker build.
- **Deployment:** Docker Compose; staging=`dev`, production=`main`; persistent host mounts for DB/uploads.

## 6. Проверки

Targeted checks first. Relevant full gates:

```bash
npm run check
npm test
npm run test:ui
npm run test:ops
npm run build
npm run test:browser
node script/check-docker-safety.mjs
docker compose build app
```

На Windows native `better-sqlite3` должен запускаться под поддерживаемым Node.js (проект/CI — Node 20). Linux-specific и Docker-проверки — через WSL, если доступны.

## 7. Release / deploy

Использовать только `docs/DEPLOY_PLAN.md`, `docs/BACKUP_PLAN.md` и существующие scripts. Production deploy выполняется только после staging, backup, успешных gates и явного разрешения владельца. Merge сам по себе не является релизом.

## 8. Human checkpoints

Обязательное решение владельца:

- push, создание PR, merge, release/deploy, force-push, удаление ветки/важных данных;
- ввод или изменение секретов/credentials;
- активация нового комплекта кейсов и политика по старым несопоставимым результатам;
- изменение продуктовой методики, профилей компетенций, порогов и UX с материально разным поведением;
- живой пилот и физическая/пользовательская приёмка;
- изменение Telegram routing registry, `thread_id` или channel override.

## 9. Автономность

Hermes самостоятельно выполняет безопасную read-only диагностику, спецификацию, декомпозицию, локальную реализацию в отдельном worktree, targeted tests и подготовку review. Codex используется для реализации/тестов, Claude Code — для архитектуры, сложной диагностики или одного независимого review. При недоступности нужного агента работа не перенаправляется стороннему провайдеру.
