# Порядок проверки

1. **Версия.** Хеш из поручения совпадает с `.git/HEAD` (или с тем, на что указывает `gitdir:`). Не совпал — `BLOCK`, «не проверено».
2. **Критерии.** Прочитать критерии готовности из поручения, проверить каждый отдельно. Не названный критерий не проверяется молча: написать, что его нет.
3. **Сам результат.** Читать дифф и файлы, не пересказ автора.
4. **Проверки.** Тесты и сборку не запускать. Смотреть журналы, приложенные к результату: команда, код возврата, версия. Нет журнала — проверка не доказана.
5. **Вердикт.** `PASS` только при доказательствах по каждому критерию. Иначе `BLOCK`.

## Что смотреть особо

- Логика оценивания, компетенции, пороги, наборы кейсов: изменение без версии и заявления о сопоставимости с прежними результатами — `BLOCK`.
- Миграции: только добавление, прежние не правятся; есть ли путь отката или резервная копия.
- Данные: нет ли в диффе секретов, `.env`, `data.db`, `live-sessions.json`, данных участников, локальных путей.
- Права: нет ли расширения доступов, обхода проверок ролей.
- Тесты: красный тест падал по правильной причине; утверждения не ослаблены ради зелёного.
- Интерфейс: правила навыка `ui-acceptance` и `AGENTS.md`.
- Объём: нет ли правок вне поручения, не сломаны ли работающие участки.

## Серьёзность замечаний

`блокирующее` — ломает критерий, данные, безопасность или оценивание. `существенное` — не ломает, но будет стоить дорого позже. `мелкое` — на усмотрение автора. `PASS` допустим с мелкими и существенными замечаниями, если они названы; блокирующее всегда `BLOCK`.
